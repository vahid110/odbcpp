# Reusable authentication library decision memo

Finite design proposal, 2026-10-03; no implementation or live admission. Companion: `REDSHIFT_AUTHENTICATION_PLAN.md`, the complete native ODBC selector inventory. Baseline public source is root2def252 plus integrated ordinary-password test a394004. This memo does not change current SDK/security contracts or accept a new universal plugin framework.

## Recommended decision

Build a small transport-independent authentication core, optional AWS/federation providers, and service-specific target adapters. Keep database framing and authenticated session ownership in the existing SDK. Use privately versioned C++ interfaces first; establish a stable external ABI only after two real consumers expose the necessary lifetime/cancellation semantics. ODBC and future ADBC consume the same library through their backend adapters; neither SQL/ODBC types nor Arrow arrays belong in the core.

The library must provide typed credentials **and** reusable challenge/proof engines where useful, rather than merely an arbitrary password callback. SCRAM transcript/proof construction, SigV4 signing and OAuth PKCE/state validation can be reusable; PostgreSQL authentication frames, Redshift token startup messages, MySQL plugin negotiation and protocol downgrade decisions remain backend-owned. Do not move existing working SCRAM/crypto code just to demonstrate abstraction. First prove a second consumer and explicit crypto-provider compatibility.

Current boundaries already support this direction: `SDK_ARCHITECTURE.md:20,25–27,92,918–940` assigns framing/authentication protocol state to backends, separates ADBC batch work, and keeps static providers free of live state. Its existing exclusion of a universal plugin framework (`:296`) should remain until root accepts a narrowly scoped revision. `SECURITY_MODEL.md:107–119` requires explicit verified TLS. `ConnectionSettings` (`core/database/i_database_connection.h:60–76`) currently owns a password string without issuer/expiry provenance; this is a real integration seam, not proof native providers exist.

## Modules and first interface shape

| Component | Responsibility and explicit exclusions |
|---|---|
| `auth_core` | Immutable method/target/trust request; bounded secret ownership; typed material; monotonic validity; typed sanitized errors; cancellation/deadline contract. No cloud calls, DSN parser, browser/process launch, ODBC diagnostics or global default chain. |
| `auth_proofs` (optional) | Audited pure SCRAM/SigV4/PKCE/state helpers through the selected private crypto adapter. No database framing, TLS connection, cloud identity discovery or issuer trust inferred from decoded JWT contents. |
| `aws_sources` (optional) | Explicit AWS key/profile/role/web-identity/SSO/process/container/instance sources, each enabled by policy; AWS credential refresh and provenance acquisition. No implicit fallthrough into newly reachable metadata/process sources. |
| `aws_issuance` (optional) | STS and exact Redshift GetCredentials/GetClusterCredentials/GetClusterCredentialsWithIAM adapters; response validation, UTC sampling and bounded calls. Method-specific permissions/principal rules stay separate. |
| `redshift_auth` | Deployment/account/region/resource/database/principal binding, native token material and API-specific policy. No assumed port/profile inference, principal auto-creation or groups/grants. |
| `rds_auth` | Explicit engine/region/actual signing endpoint/port/database user and resource permission binding; local IAM signed-token generation. Not Redshift issuance and not a promise all Redshift IdPs work on RDS. |
| `federation` (optional packages) | Separate SAML/password IdP, OAuth/native JWT and Identity Center adapters. Validated endpoint/audience/issuer/scopes and exact configured flow; no catch-all arbitrary provider loader. |
| Caller interaction / secret-store adapters | Caller supplies approved browser interaction or protected external tokens/OS secret-store access. UI, desktop policy, OS keychain prompts and process trust remain explicit optional boundaries. |
| SDK/session owner | Converts typed material to backend protocol, verified peer binding, publication, leases, reconnect/pool policy and final ODBC/ADBC error mapping. |

Illustrative API values, not an approved shared header: immutable `AuthRequest{method, target, trust_policy, interaction_policy, original_deadline}`; `AcquireResult` carrying a move-only `CredentialMaterial` variant (ordinary password, temporary DB credentials, native subject token, AWS signing credentials or RDS token) plus provenance receipt and acquisition validity. An explicitly injected issuer/source is responsible for verified response provenance. A caller setting `verified=true`, a port number, decoded token, or current local CredentialContext cannot establish AWS provenance.

Material exposes only scoped consumption, never a debug/string serializer. Success includes exact returned identity and method; unsupported, denied, malformed, expired, cancelled and unavailable remain distinct sanitized categories. Native server failures remain available through the SDK's existing owning error path with bounded diagnostic handling. Limit individual opaque credential bytes locally for resource safety without claiming an AWS service maximum; reject truncation and NUL where protocol forbids it. RDS tokens are often over1KiB, so fixed short password buffers are unacceptable. Public AWS and private source errors must never expose tokens, DSNs or raw HTTP bodies.

Future C ABI, if needed: version/size-tagged options, opaque move/release handles, explicit cancellation and bounded errors; no STL types across ABI. ADBC's [versioned C specification](https://arrow.apache.org/adbc/current/format/specification.html) is a consumer precedent, not an authentication-provider standard we can claim to implement now.

## Identity, time and sessions

Freeze deployment identity, resource IDs, database/principal policy, TLS hostname/trust policy and method at admission. AWS permissions/source identity, issuer endpoint/audience and groups/AutoCreate options are part of binding, not ambient defaults. Response APIs do not all echo resource/account; trusted request/response acquisition and independent target readback must bind them. Preserve GetClusterCredentials' returned IAM:/IAMA: principal distinction; do not normalize away security identity. `NextRefreshTime` is API-specific (WithIAM documents it reserved), not universal expiry permission.

For temporary material, translate service UTC expiry to a conservative monotonic bound using a trusted UTC sample bracketed by monotonic reads and explicit clock uncertainty. A candidate formula is `m_before + floor(expiry_utc - sample_utc - uncertainty)` with checked bounded arithmetic. Reject unknown uncertainty, future/stale samples, invalid timestamps and exclusive-bound equality. Subsequent wall-clock rollback cannot extend a published bound; suspend/drift assumptions require defined resampling policy. Require the original **authentication/connect** deadline plus headroom inside this bound when new authentication needs valid material. This does not mean every query must finish before credential expiry.

[RDS IAM documentation](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.IAMDBAuth.html) specifies15-minute SigV4 authentication tokens. Token expiry controls new authentication, not a claimed server-forced close of already authenticated sessions. Redshift open-session lifetime behavior must likewise be sourced/proved separately; issuer expiry alone is insufficient. Pool/session-owner policy can retire sessions conservatively, but must label that as client policy. Reconnect and cleanup requiring a new connection each need independently valid credentials. Never silently rebind a physical session to rotated identity.

Current `CredentialContext` (`core/database/credential_context.cpp:28–44`) implements exclusive local expiry/revocation and generation authority; it is not issuer provenance. SessionOwner generation/lease mechanics should consume an admitted receipt without pretending a new token reauthenticates an existing session. Current `GenericDatabaseConnection` connect deadline and secret-cleanup paths (`core/database/generic_database_connection.cpp:184–282,985–1085`) and parser verified-peer/downgrade checks (`core/database/postgres/pg_protocol_parser.cpp:410–455`) stay intact.

## Refresh, concurrency, interaction and secrets

Cache only where the exact method permits it; key by issuer/source generation, method, deployment/resource/database/principal, trust policy, requested role/groups/scopes and interaction policy. Never use only username or cache a raw secret/JWT in the key/log. A per-key single-flight coordinator may coalesce refresh; hold no global/cache mutex during network, process, browser or caller callbacks. Each waiter retains its own original deadline/cancellation; a late waiter cannot extend existing work. Bound retries explicitly and do not retry denied authentication through other methods. Publish new immutable material atomically; invalidation/rotation cannot mutate material already consumed by a different physical session. Use expiry-aware bounded negative caching only where it cannot mask credential rotation. Refresh thresholds are scheduling hints, never extensions of service validity.

Explicit interaction policies: `headless_external_only`, `headless_approved_sources`, and `interactive_approved_browser`. Headless runs must reject unsupported browser/OS prompts before side effects. Caller-approved browser callbacks receive bounded public challenge data; no secret URL logging. Local callbacks require method-specific loopback binding, state/nonce/PKCE, expected path/issuer, single-use acceptance, timeout and cancellation. Do not assume a mobile browser can reach a desktop loopback listener or add device-code flows absent the selected reference contract. Password/MFA IdP clients require explicit tenant/admin policy and no hidden conditional-access bypass.

AWS metadata, external executables and secret stores require separate capability permissions. Windows upstream executable fallback is a compatibility obligation, not permission to run arbitrary DSN programs. A future adapter needs approved executable identity/path, no shell, bounded input/output/lifetime, protected handoff and child cleanup; preserve the Windows-only scope until separately reviewed. Upstream process command-line arguments and default TLS behavior must not be copied without security review.

Secrets are move-only owned buffers with scoped views, cleansing on release/failed acquisition/cancellation and no ordinary copying/formatting APIs. This reduces exposure; it cannot promise every OS/SDK/internal string copy is erased. Audit SDK allocations, crash dumps, subprocess arguments, swap and diagnostic logs explicitly. TLS for IdP/STS APIs is a separate channel from DB TLS, but both must verify chain and hostname using approved trust. Proxy/custom endpoint settings cannot downgrade trust. Existing AWS-LC/OpenSSL linkage profile ownership remains root's; no user-loaded crypto libraries.

## Federation verification authority and initial scope

Each method must name its cryptographic verification authority in a reviewed trust matrix. For SAML, use a maintained parser with DTD/external entities disabled and bounded document size/depth; do not implement XML signature handling ad hoc. Signature/reference integrity (including wrapping attacks), issuer, audience, recipient/destination, time conditions and replay require either an audited local verifier or explicit delegation to the selected STS/Redshift service. Parsing attributes or a successful HTTPS download does not establish assertion authentication. Preserve an assertion as unverified material until the designated authority accepts it.

For OIDC/JWT, a local verifier must enforce an explicit algorithm/key policy, trusted issuer and bounded trusted JWKS retrieval/rotation, audience, time and applicable nonce/state/replay rules. Never fetch a token-controlled key URL or treat decoded claims as proof. Methods delegating token validation to Redshift/Identity Center must say so and preserve that trust boundary; opaque access tokens cannot be relabeled locally verified JWTs. Browser OAuth must bind its authorization response and token exchange with the exact registered redirect, PKCE/state and applicable nonce. These method-specific trust contracts and adversarial tests precede any federation adapter implementation.

The first slice has no cache, background refresh, browser/process launch, network credential discovery or relocation of working proof code. It implements immutable target/source policy, move-only secret and typed material/receipt, injected clock/deadline admission, safe errors/redaction and deterministic tests. One exact issuer adapter is a separately reviewed successor. Single-flight/caching stays deferred until a coordinator contract defines per-waiter cancellation, shared-work lifetime and cancellation when all waiters leave. One waiter must not cancel another's acquisition; a later waiter must not extend the original shared deadline. No cache may be enabled before these rules are independently tested.

## Dependencies, packaging and qualification

Prefer optional pinned AWS SDK adapters over inventing STS/credential-chain implementations. Upstream README calls SDK1.11.895 “last tested”; it is not a dependency lock or our required version. Resolve exact SDK components, retry/timeouts/cancellation, credentials-chain order, crypto/HTTP linkage, platform support, binary size and SBOM before acceptance. [AWS SDK source/license](https://github.com/aws/aws-sdk-cpp/blob/main/LICENSE) is Apache2.0; transitive dependencies/notices/distribution and FIPS assertions require independent packaging review. Separate provider-free builds must remain usable, with standalone auth-core dependency/build tests. Each optional adapter needs packaging/link/load tests against existing OpenSSL and AWS-LC profiles: no hidden second TLS stack, conflicting symbols or changed distribution notices. Windows/macOS/Linux browser/OS store/process behavior needs distinct qualification; source presence does not establish platform acceptance. Do not freeze an external ABI before Redshift, RDS and an ADBC consumer prototype expose the actual contract.

RDS is a distinct adapter: [permissions](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.IAMDBAuth.IAMPolicy.html) use `rds-db:connect` and dbuser resource identity; signing binds actual endpoint, region, port and DB user. Custom Route53 aliases cannot replace the required signing hostname. Engine/version/region enablement, PostgreSQL rds_iam precedence and unsupported combinations are explicit target policy. RDS proxies are a separate researched profile. No claim all IdPs, Redshift groups or AutoCreate semantics transfer to RDS.

Substantive reusable CI: deterministic fake issuers/clocks/HTTP/process/browser boundaries; malformed/error/expired/unknown provenance; exact-target mismatch; expiry equality/rollback/suspend/overflow; cancellation during every phase; concurrent refresh/rotation/cache-isolation; secret redaction/cleanse and bounded payloads; hostile callback/state/PKCE/endpoint/proxy cases. Retain existing parser/liveness/session tests rather than manufacture duplicate happy-path suites. Test SDK adapters against controlled HTTP fixtures and separately against authorized real services. All-method live matrix needs each native selector's ordinary-user identity, denied/expired/refresh/reconnect behavior, exact official-driver differential, platform and Driver Manager packaging. Skipped unavailable IdPs are gaps, never qualified green cases.

## PostgreSQL Kerberos requirement and delivery policy

PostgreSQL Kerberos authentication is an additional required roadmap capability. Plan optional GSSAPI adapters on supported platforms and Windows SSPI interoperability, while retaining PostgreSQL authentication-message framing in the backend. The reusable library owns scoped OS security contexts and token-step/cancellation contracts; it must not export protocol handles or assume Kerberos is merely another password provider. PostgreSQL GSS authentication and GSS transport encryption are distinct scopes. Do not silently negotiate NTLM when a caller explicitly requires Kerberos; credential delegation is separately controlled and disabled by default.

Before implementation, audit service-principal/hostname/realm binding, ticket-cache and OS-login credential sources, mutual authentication, mechanism policy, bounded multi-step tokens, expiry/new-login versus established-session semantics, TLS/channel protection, cancellation and optional dependency packaging. Tests need deterministic token-step failures plus real KDC/PostgreSQL and Windows-domain fixtures, including wrong service/realm, expired/missing tickets, denied principal mapping, delegation policy, concurrency and recovery. These are future qualification requirements, not current support.

Sources: [PostgreSQL GSSAPI](https://www.postgresql.org/docs/current/gssapi-auth.html), [PostgreSQL SSPI](https://www.postgresql.org/docs/current/sspi-auth.html), [connection controls](https://www.postgresql.org/docs/current/libpq-connect.html). Exact OS/provider/version support must be verified; an IdP brand name alone does not establish platform restrictions.

All Redshift methods remain mandatory eventual parity targets, implemented in separate packages at the appropriate time. PostgreSQL Kerberos planning must inform the library boundary now; it does not preempt the current Redshift catalog and MySQL implementation packages or enable new realm/domain/cloud authority.
