# ODBC API trace and logging ownership

Status: implemented on `codex/redshift-odbc-trace`; product-neutral, delivered to
the Redshift product through normal composition. User configuration is in the
README section "ODBC API trace".

## Ownership

| Concern | Owner | File |
| --- | --- | --- |
| Sinks, rotation, format, escaping, bounds, field sensitivity/redaction | SDK | `sdk/internal/odbcpp/util/driver_logging.h`, `sdk/src/util/driver_logging.cpp` |
| Public label for a backend error (closed vocabulary of fixed literals) | Backend | `BackendError::public_reason` set in `core/database/postgres/redshift_*` |
| ODBC signatures, handles, diagnostics, argument roles, trace records | ODBC adapter | `odbc/odbc_trace.h`, `odbc/odbc_trace.cpp`, `odbc/odbc_api.cpp` |

Before this change the adapter matched Redshift backend message prefixes
("Invalid Redshift schema metadata: ...") to choose `catalog_reason` log
labels, so backend knowledge lived in shared ODBC code. The backend now
publishes `BackendError::public_reason` (for example `schema.show-rows`) built
only from its own fixed literals. The adapter publishes it after a shape check
(`[a-z0-9.-]`, at most 64 bytes) and never inspects the message.

SDK additions are generic: a `std::span<const LogField>` overload of
`DriverLogger::log`, a shared `parse_flag`, and `LoggingOptions::log_sensitive`.
Only trusted process configuration sets that option; `LoggingOptions::resolve`
never reads it from driver, DSN or connection parameters.

No generic call-tracing abstraction was added to the SDK. API tracing is ODBC
adaptation, and ODBCPP has no second client adapter today.

## Design

- **Interceptor at the single C entry chokepoint.** Every exported function is
  generated by the `ODBCPP_API_*` / `ODBCPP_DIAG_API_*` macros. Each macro wraps
  its guarded call in `trace::traced_call`, outside the handle lease, so the
  trace records the application's arguments and the final return code. The
  cancellation entry points, which bypass the lease, are wrapped explicitly.
  Only the outermost call is traced (`detail::api_call_depth`).
- **Declarative signature table.** The C type alone cannot tell SQL text from an
  identifier, a password or an output buffer, and unixODBC's `SQLWCHAR` is the
  same type as `SQLUSMALLINT`. So `odbc_trace.cpp` declares a role for each
  parameter of each exported function (`ArgRole`). The ANSI and wide variants
  share one signature; the captured pointee width selects narrow or `SQLWCHAR`
  decoding. A GoogleTest checks that the table equals `odbc/odbcpp.exports` and
  that every entry's argument count equals the compile-time arity of the
  exported function.
- **Type erasure at the boundary.** `capture<T>` turns each argument into an
  `ArgValue` (signed, unsigned or address, plus pointee width). All rendering
  is ordinary non-template code driven by the roles.
- **Process-wide, lazily resolved tracer.** `Tracer::active()` resolves trusted
  configuration once, on the first ODBC call. When tracing is disabled it costs
  one atomic load. Configuration keys are translated to the SDK logger
  vocabulary so the SDK's validation, sinks and bounds apply unchanged.
  Tracer storage is never freed, so ODBC calls made from an application's
  static destructors stay safe. A shutdown guard still closes the sink when the
  driver unloads or the process exits, which matters because Driver Managers
  unload and reload drivers, and it leaves tracing Disabled afterwards. Any
  failure while resolving or opening the sink also leaves tracing Disabled, so
  it is never retried on each call.
- **Security.** Secrets are dropped, including the field key. Connection
  strings are masked and then Sensitive. Identifiers and text values are
  Sensitive. SQL text uses the QueryText classification. Data buffers are shown
  only as addresses. Output values are read only after `SQL_SUCCESS` or
  `SQL_SUCCESS_WITH_INFO` (and the `SQLParamData` token on `SQL_NEED_DATA`).
  Reads are bounded by the application's declared lengths, the capacity of its
  buffers and 4096 units.
  Connection-string length arguments are dropped because they reveal the
  password length. An unterminated braced value masks the remainder of the
  string. `NumericAttributePtr` is shown as an address because it is written
  only for numeric fields. With `ODBCTraceSensitive=true`, diagnostic
  `MessageText` (Sensitive) may echo SQL even when `ODBCTraceQueries` is off.

## Recommendation: pre-connection and connection-failure logging

The per-connection logger already exists for most connect failures: it is
created right after `ConnectionString::resolve` in `ODBCConnection::connect`, so
DSN lookup, transport, TLS and authentication failures emit `connection_failed`.
These gaps remain:

1. ODBC activity before any connect (`SQLAllocHandle`, `SQLSetEnvAttr`,
   pre-connect `SQLSetConnectAttr`). The process trace above now covers it.
2. Rejections that happen before that logger exists: unknown connection keywords
   (`odbc/odbc_api.cpp`), embedded NUL or parse errors, DSN or driver-config
   read failures, and an invalid logging configuration
   (`LoggingOptions::resolve` throws).

Recommended follow-up. This is an incremental change, not a redesign:

- **Two logging tiers.** The process tier is configured only from the driver
  section and the environment (the same trusted resolver as the trace). The
  connection tier is today's logger, refined by DSN and connection-string
  settings.
- **Fallback routing.** `ODBCConnection::log` and `detail::log_api_result` use
  the connection logger when it exists, otherwise the process logger. When
  neither exists the record is dropped, as now. Logging-configuration errors
  still reach the application through ODBC diagnostics, which remain the
  authoritative channel.
- Create the connection logger as early in `connect()` as resolution allows.
- **Do not add a temporary log file.** `SECURITY_MODEL.md` requires log
  destinations to be trusted configuration. A driver-chosen path creates
  permission, cleanup and leakage risk. Records written before the
  connection's settings are known could also violate its redaction, query and
  level policy.
- **Optional: buffer and replay.** If early events must follow the connection's
  own policy, keep a small bounded in-memory buffer of owning records, each with
  its sensitivity. When the connection logger is created, replay the buffer
  through it; if logging resolves to Off, discard it. That buffer is a generic
  SDK component in `driver_logging`. Its keys must be owned or static.

## Remaining limits

- When tracing is enabled, every traced call takes one process mutex to copy
  the tracer. This is accepted while tracing; the disabled path is lock-free.
- The exit SQLSTATE is read after the handle lease is released. A concurrent
  call on the same handle can replace it.
- Thread identifiers are native on Windows and a hash on POSIX.
- Text records show `connection_id=0`; the handle arguments identify the
  connection.
- Attribute `ValuePtr` and info buffers are shown as addresses, not decoded per
  attribute.
- Unchanged pre-existing behavior: the connection logger still accepts
  `LogFile` from connection strings.
